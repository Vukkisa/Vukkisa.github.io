KnowYourRules

400+ documents went in.
A smaller, curated knowledge base came out.
Then came retrieval.

A RAG assistant for Indian traffic law. It answers only from official documents and refuses when they run out. Ask it something, and watch how far your question gets.

each square is a document, kept or dropped · proportions illustrative

A toy keyword retriever over 7 paraphrased sample chunks, standing in for embeddings and Chroma. It shows the retrieve-or-refuse decision. It is not the live system, and not legal advice.

the problem
Traffic rules live in dense legal documents. People ask forwarded messages and search engines instead, and get confident, half-remembered answers. I wanted answers from the official text, with the source attached.
what I built
Documents are cleaned, chunked and embedded (nomic-embed-text via Ollama) into Chroma. A LangChain LCEL chain retrieves context for a Groq-hosted LLM. FastAPI serves it to a plain HTML/JS frontend.
the hard part
The refusal path. Getting a model to say "I can't answer that from these documents" reliably, instead of helpfully inventing something. And deciding what, out of 400+ documents, deserves to stay.
what I learned
Retrieval quality is mostly decided before the model runs: in extraction, cleaning and chunking. A good "no" has to be designed and tested like any other feature.
what I'd change
An evaluation set of questions with known answers and known refusals. Hybrid search with a reranker. Page-level citations.

Unauthorized Human Detection

A camera sees everything.
Almost none of it matters.

Real-time person detection with YOLOv8 and OpenCV on a webcam, video file or RTSP stream. Zones can be redrawn on the fly, and events are logged with snapshots. About 35 FPS, 24 ms per frame, with CUDA.

event log

    Drag the zone's corners. This is a simulation: random walkers and a point-in-polygon test. The real system runs YOLOv8 on actual video.

    the problem
    Spaces that should be empty sometimes aren't, and nobody watches a feed all day. I wanted something that watches for me and speaks up only when a person is somewhere they shouldn't be.
    what I built
    YOLOv8 and OpenCV over three kinds of source, dynamic zones, and event logging that saves snapshots and clips as evidence. CUDA-optimised to roughly 35 FPS.
    the hard part
    Latency, not accuracy. Keeping capture, inference and logging from blocking each other, and stopping one person standing still from producing a hundred events.
    what I learned
    The model is a small part of a vision system. The rest is I/O, threading, thresholds and deciding what counts as an "event".
    what I'd change
    Tracking IDs across frames, re-identification so "unauthorised" can mean a specific someone, and a small dashboard for reviewing events.

    Ez-Learn

    One tab for videos, one for payments, one for progress.
    I wanted one door.

    browser → router → view → database → payment → unlocked course

    the problem
    Learning platforms often scatter videos, progress, payments and instructors across disconnected tools. I wanted the student's journey to be one flow.
    what I built
    A Django platform: course catalogue and enrolment, secure payments, a student dashboard and an admin panel, deployed on Render. It began as an internship project at TalentSprint.
    the hard part
    Payments. The happy path is a button. The real work is confirming success on the server, handling failure, and never unlocking a course for an unpaid order.
    what I learned
    How a web app behaves in production: environment config, migrations, static files. Deploying is part of building.
    what I'd change
    Tests around the payment flow, a recommendation module (the architecture is ready for one), and better progress analytics.
